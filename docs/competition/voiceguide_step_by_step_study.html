VoiceGuide 단계별 전체 학습 워크북

이 문서는 프로젝트를 “기능 목록”으로 외우지 않고, 사용자가 앱을 켰을 때부터 Android, YOLO 모델, 위험도 판단, TTS/진동, 서버 저장, 대시보드까지 어떤 순서로 이어지는지 설명하기 위한 공부 자료입니다.

추천 사용법: 각 섹션을 읽은 뒤 빈 답변 칸에 직접 한 문장으로 적고, 코드 파일을 열어서 같은 이름의 함수와 클래스를 확인합니다.

0. 공부 방식: 풀악셀 금지의 실제 의미

강사님이 말한 “풀악셀 밟지 말라”는 말은 기능을 줄이라는 뜻이 아니라, 이해 순서를 지키라는 뜻에 가깝습니다. 이 프로젝트는 Android, AI 모델, 서버, DB, 대시보드, 테스트가 섞여 있어서 곧바로 전체 코드를 보면 길을 잃기 쉽습니다.

공부 원칙: 화면과 흐름을 먼저 이해하고, 그 다음 파일 역할을 이해하고, 마지막에 함수 내부를 봅니다.
1단계: 이 기능이 사용자에게 어떤 도움을 주는지 말합니다.
2단계: 데이터가 어디에서 시작해서 어디로 이동하는지 그립니다.
3단계: Android와 서버의 역할을 분리합니다.
4단계: 각 파일이 맡은 역할을 한 문장으로 설명합니다.
5단계: 중요한 함수만 열어서 입력, 처리, 출력을 확인합니다.
6단계: 테스트와 리포트로 “동작한다”는 근거를 확인합니다.

서버에서 감지합니다. 감지는 Android에서 하고, 서버는 감지 JSON과 GPS를 저장하고 대시보드에 보여줍니다.

1. 1분 설명부터 만들기

프로젝트를 깊게 이해하려면 먼저 짧게 설명할 수 있어야 합니다. 아래 문장을 기본값으로 외운 뒤, 각 단어가 어떤 코드와 연결되는지 찾아가면 됩니다. 

VoiceGuide는 스마트폰 카메라로 전방 객체를 감지하고,
Android 안에서 위험도를 판단해 TTS와 진동으로 즉시 안내하는 보행 보조 MVP입니다.
감지 결과와 GPS는 서버로 보내 저장하고,
대시보드에서는 세션별 위치, 탐지 이력, 위험 구간을 확인합니다.

1분 설명을 4문장으로 쪼개기

  1. 문제: 시각장애인이 이동 중 전방 장애물과 위험 객체를 빠르게 인지하기 어렵습니다.

  4. 운영 근거: 서버와 대시보드는 감지 결과, GPS, 이력을 저장하고 시연 증거를 제공합니다.

2. 전체 지도: 데이터가 흐르는 길

이 프로젝트의 중심은 “카메라 프레임이 사용자 안내와 서버 기록으로 바뀌는 과정”입니다. 아래 흐름을 외우면 대부분의 파일 위치가 자연스럽게 이해됩니다. 

[스마트폰 카메라]
  -> CameraX 프레임
  -> TfliteYoloDetector
  -> Detection 목록
  -> MvpPipeline
  -> riskScore / distanceM / vibrationPattern
  -> SentenceBuilder
  -> 한국어 TTS 문장
  -> MainActivity
  -> 화면 bbox + TTS + 진동 + GPS + 서버 업로드

[FastAPI 서버]
  -> /detect 또는 /detect_json
  -> 객체 JSON 정규화
  -> SessionTracker
  -> DB 저장
  -> SSE 이벤트 발행
  -> dashboard.html 실시간 표시
중요: 현재 구조에서 서버는 카메라 이미지를 받아 YOLO 추론하는 서버가 아닙니다. Android가 이미 감지한 결과를 서버에 보내고, 서버는 저장과 대시보드 역할을 합니다.

역할 분리

Android가 책임지는 것

  • 카메라 프레임 수집
  • TFLite YOLO 온디바이스 추론
  • 위험도 계산과 진동 패턴 결정
  • 한국어 TTS 안내
  • GPS 수집과 서버 업로드

서버가 책임지는 것

  • 정책 JSON 제공
  • 감지 JSON 정규화
  • DB 저장
  • 세션별 상태 추적
  • 대시보드와 SSE 실시간 이벤트

3. 폴더와 파일을 지도처럼 보기

처음부터 모든 파일을 읽지 말고, 아래 표에서 “어느 폴더가 어느 책임을 갖는지” 먼저 봅니다.

경로무엇을 담고 있는가공부할 때 보는 관점

4. 실제 실행 흐름을 한 프레임 기준으로 뜯기

“앱이 실행된다”를 한 번에 이해하려 하지 말고, 카메라 프레임 하나가 들어왔을 때 무슨 일이 생기는지 봅니다.

프레임 입력: CameraX가 현재 카메라 이미지를 가져옵니다.
모델 입력 변환: 이미지를 YOLO 모델이 기대하는 320x320 입력으로 맞춥니다.
추론: TFLite Interpreter가 객체 후보를 출력합니다.
후처리: confidence, bbox, NMS/출력 형식에 맞춰 Detection 목록을 만듭니다.
위험도: MvpPipeline이 거리, 중심성, 클래스 가중치로 risk score를 계산합니다.
사용자 안내: SentenceBuilder가 문장을 만들고 MainActivity가 TTS와 진동을 실행합니다.
기록: 필요하면 서버에 탐지 JSON과 GPS를 보냅니다.

한 프레임을 설명할 때 꼭 들어가야 할 단어

CameraX TFLite Detection bbox riskScore TTS vibration POST /detect

5. Android 앱 코드 뜯기

Android는 이 프로젝트의 사용자 경험 중심입니다. 서버가 잠깐 없어도 기본 안내가 가능해야 하므로, 카메라와 YOLO와 TTS는 Android 안에서 돌아갑니다.

파일역할읽을 때 질문
MainActivity.kt 앱의 중앙 제어 장치. 카메라, STT, TTS, 진동, GPS, 서버 업로드를 연결합니다. 프레임이 들어오면 어디서 분석을 시작하고, 성공/실패를 어떻게 처리하는가?
TfliteYoloDetector.kt TFLite 모델 로딩, 이미지 전처리, 추론, 후처리 담당 모델 입력 크기와 출력 형식을 어떻게 처리하는가?
MvpPipeline.kt IoU tracking, EMA smoothing, bbox 기반 거리, 위험도, 진동 패턴 담당 YOLO 결과를 사용자에게 의미 있는 위험 정보로 바꾸는 기준은 무엇인가?
SentenceBuilder.kt 탐지 객체를 한국어 TTS 문장으로 변환 어떤 객체를 먼저 말하고, 거리는 어떻게 표현하는가?
VoicePolicy.kt 정책 JSON 로딩, 서버 정책 캐시, 거리 포맷, 클래스 기준 제공 서버 정책과 로컬 기본 정책이 어떻게 연결되는가?
BoundingBoxOverlay.kt 카메라 화면 위 bbox 표시 정규화 좌표를 화면 좌표로 어떻게 되돌리는가?
Detection.kt 탐지 결과 데이터 구조 객체 하나를 표현하기 위해 어떤 필드가 필요한가?

Android를 공부하는 순서

  1. Detection.kt로 데이터 모양을 먼저 봅니다.
  2. TfliteYoloDetector.kt에서 모델이 Detection을 만드는 과정을 봅니다.
  3. MvpPipeline.kt에서 Detection에 위험도와 trackId가 붙는 과정을 봅니다.
  4. SentenceBuilder.kt에서 Detection이 문장으로 바뀌는 과정을 봅니다.
  5. MainActivity.kt에서 이 조각들이 실제 앱 흐름으로 연결되는 것을 봅니다.
외울 문장: MainActivity는 모든 계산을 직접 하는 파일이 아니라, 카메라, 모델, 파이프라인, 문장 생성기, TTS/진동, 서버 업로드를 이어주는 중앙 제어 파일입니다.

6. YOLO/TFLite 모델 이해

YOLO 모델은 “앞에 무엇이 있는지”를 알려줍니다. 하지만 YOLO만으로는 사용자에게 바로 안내할 수 없습니다. 감지 결과를 거리, 위험도, 문장, 진동으로 바꾸는 후처리가 필요합니다.

모델 파일

파일역할
android/app/src/main/assets/yolo11n_320.tflite 기본 온디바이스 YOLO 모델. 앱이 먼저 이 파일을 찾습니다.
android/app/src/main/assets/yolo26n_float32.tflite fallback 모델. 기본 모델이 없을 때 사용할 수 있는 보조 모델입니다.
android/app/src/main/assets/policy_default.json 서버 정책을 못 받아도 앱이 기본 판단 기준을 갖도록 하는 로컬 정책입니다.

모델이 하는 일과 하지 않는 일

모델이 하는 일

  • 이미지에서 객체 후보를 찾습니다.
  • 각 객체의 class, confidence, bbox를 만듭니다.
  • 프레임마다 현재 보이는 객체 정보를 제공합니다.

모델이 하지 않는 일

  • 사용자에게 말할 문장을 직접 만들지 않습니다.
  • 위험도 점수를 최종 결정하지 않습니다.
  • GPS를 저장하거나 대시보드를 만들지 않습니다.

설명할 때 중요한 포인트

  • 모델 입력은 정사각형 320 크기에 맞춰야 합니다.
  • 카메라 화면 좌표와 모델 입력 좌표는 다르기 때문에 좌표 변환이 필요합니다.
  • confidence가 높다고 항상 사용자에게 가장 위험한 것은 아닙니다.
  • risk score는 클래스, 거리, 중심성, bbox 크기를 함께 봅니다.

7. 위험도, 추적, 진동 파이프라인

MvpPipeline.kt는 발표에서 꼭 설명해야 하는 핵심입니다. YOLO가 “객체 후보”를 만들면, 파이프라인은 그 후보를 “사용자에게 알려야 할 위험”으로 바꿉니다.

파이프라인이 필요한 이유

  • YOLO bbox는 프레임마다 조금씩 흔들립니다.
  • 같은 물체가 매 프레임 새 물체처럼 보이면 TTS가 계속 반복될 수 있습니다.
  • 사람에게 필요한 것은 모든 객체가 아니라 “지금 조심해야 할 객체”입니다.
  • 진동은 위험도 단계에 따라 다르게 느껴져야 합니다.

주요 개념

개념뜻설명 포인트
IoU Tracking 이전 프레임의 bbox와 현재 bbox가 얼마나 겹치는지 보고 같은 객체인지 판단 같은 객체에 같은 trackId를 유지해서 안내 안정성을 높입니다.
EMA Smoothing 새 값과 이전 값을 섞어서 흔들림을 줄이는 방식 bbox와 거리 추정이 갑자기 튀는 것을 줄입니다.
bboxDistanceM bbox 크기 기반 거리 추정 bbox가 클수록 가까운 물체로 추정합니다.
riskScore 위험 정도를 0~1에 가깝게 표현하는 점수 거리, 중심성, 객체 종류, 크기를 함께 봅니다.
VibrationPattern NONE, SHORT, DOUBLE, URGENT 같은 진동 단계 사용자가 화면을 보지 않아도 위험 단계를 느낄 수 있게 합니다. 
YOLO Detection
  -> 같은 객체인지 추적
  -> 흔들림 완화
  -> bbox 기반 거리 계산
  -> class/center/distance 기반 risk score 계산
  -> 진동 패턴 선택
  -> TTS 문장 우선순위 결정

8. TTS와 음성 명령 이해

VoiceGuide의 핵심은 “봤다”가 아니라 “사용자가 바로 이해했다”입니다. 그래서 감지 결과는 반드시 한국어 문장과 진동으로 바뀌어야 합니다.

문장 생성

파일역할
android/.../SentenceBuilder.kt Android 온디바이스 모드에서 바로 읽을 한국어 문장을 만듭니다.
src/nlg/sentence.py 서버 테스트와 질문 응답에서 사용할 수 있는 문장 생성 로직입니다.
src/nlg/templates.py 방향, 조사, 문장 템플릿 관련 보조 로직입니다.

좋은 안내 문장의 조건

  • 너무 길지 않아야 합니다.
  • 가장 중요한 위험부터 말해야 합니다.
  • 거리와 방향이 사용자에게 직관적으로 들려야 합니다.
  • 같은 안내를 너무 자주 반복하지 않아야 합니다.
  • 물건 확인 질문 같은 즉답은 일반 안내보다 우선할 수 있어야 합니다.
설명 문장: TTS는 단순히 텍스트를 읽는 기능이 아니라, 위험도와 사용자 피로도를 고려해서 무엇을 언제 말할지 조절하는 사용자 경험 장치입니다.

9. 정책 파일과 기준값 이해

프로젝트에서 “무엇을 위험하다고 볼 것인가”는 코드에 흩어져 있으면 관리가 어렵습니다. 그래서 정책 JSON을 두고 서버와 Android가 같은 기준을 공유하도록 구성했습니다.

파일역할
src/config/policy.json 서버가 제공하는 기준 정책입니다.
src/config/policy.py 서버에서 정책을 로드하고 필요한 집합과 임계값을 꺼내는 코드입니다.
android/app/src/main/assets/policy_default.json 서버 연결 전에도 Android가 사용할 수 있는 기본 정책입니다.
VoicePolicy.kt Android에서 정책을 읽고 캐시하고 거리 포맷과 클래스 기준을 제공합니다.

정책에 들어가는 대표 기준

  • 차량, 동물, 주의 객체, 일상 객체 목록

  • bbox 기반 거리 보정값
  • 손에 든 물건, 가까운 물건, 전방 물건 판단 기준
  • 서버와 Android가 지원하는 정책 버전

10. FastAPI 서버 뜯기

서버는 “YOLO 서버”가 아니라 “기록, 정책, 대시보드, 검증 서버”입니다. 이 차이를 정확히 말할 수 있어야 전체 구조를 제대로 이해한 것입니다.

src/api/routes.py 정책, detect, gps, status, events, dashboard API Android 요청이 들어오면 어떤 순서로 처리되는가?
src/api/db.py SQLite/PostgreSQL 저장, 조회, 이력, heatmap, route 저장 탐지 이벤트와 GPS가 어떤 테이블 성격으로 저장되는가?
src/api/tracker.py 세션별 객체 상태 안정화, voting, 최근 상태 유지 대시보드와 질문 응답을 위해 최근 상태를 어떻게 유지하는가?

11. DB와 대시보드 이해

DB와 대시보드는 사용자에게 직접 소리를 내는 기능은 아니지만, 프로젝트를 검증하고 시연하는 데 매우 중요합니다. “앱이 현장에서 무엇을 봤는지”를 기록으로 남기기 때문입니다.

DB에 남는 것

  • 세션 ID
  • 탐지 객체 목록
  • class, confidence, bbox, distance, risk score
  • GPS 좌표
  • 탐지 이벤트 시간
  • 성능 지표와 alert decision
  • 저장된 이동 경로

대시보드가 보여주는 것

  • 현재 세션의 위치
  • 최근 탐지 객체
  • GPS 이동 경로
  • 최근 24시간 탐지 이력
  • 위험 구간 heatmap
  • 팀 위치와 최근 세션 목록
발표 포인트: 대시보드는 앱의 핵심 안내 기능이 아니라, 시연과 운영 검증을 위한 관찰 화면입니다.

15. 7일 공부 계획

양이 많아도 괜찮습니다. 대신 순서를 정해서 매일 “말로 설명할 수 있는 범위”를 늘려가면 됩니다.

날짜공부 범위완료 기준
1일차 전체 흐름, 폴더 구조, 1분 설명 Android와 서버 역할을 분리해서 말할 수 있다.
2일차 Detection.kt, TfliteYoloDetector.kt, 모델 assets 카메라 프레임이 Detection 목록이 되는 과정을 말할 수 있다.

4일차 SentenceBuilder.kt, src/nlg, TTS 흐름 탐지 결과가 한국어 안내 문장으로 바뀌는 기준을 설명할 수 있다.
5일차 MainActivity.kt 앱의 중앙 제어 흐름을 큰 덩어리로 설명할 수 있다.
6일차 src/api, DB, dashboard 서버가 추론이 아니라 저장/대시보드 역할이라는 점을 설명할 수 있다.
7일차 tests, tools, 성능 리포트, 발표 질문 대비 검증 근거와 한계/개선 방향을 말할 수 있다.

16. 강사님 질문 대비

아래 질문에 답할 수 있으면 “프로젝트를 단계별로 이해했다”고 볼 수 있습니다.

기본 구조 질문

질문핵심 답변
이 프로젝트는 한 문장으로 뭐예요? 스마트폰 카메라와 온디바이스 YOLO로 전방 객체를 감지하고 TTS/진동으로 안내하는 보행 보조 MVP입니다.
서버가 YOLO를 돌리나요? 아니요. 현재 구조는 Android가 YOLO를 돌리고, 서버는 JSON 저장과 대시보드 표시를 담당합니다.
왜 온디바이스 추론인가요? 보행 중 안내는 지연이 작아야 하고, 네트워크가 불안정해도 기본 안내가 가능해야 하기 때문입니다.

기술 질문

질문핵심 답변
YOLO 결과를 그대로 말하지 않는 이유는? 모든 객체를 말하면 피로도가 높고, bbox 흔들림도 있어서 위험도와 우선순위 후처리가 필요합니다.
riskScore는 confidence와 같은가요? 아닙니다. confidence는 모델 확신도이고, riskScore는 거리, 중심성, 객체 종류, 크기를 함께 본 서비스 위험도입니다.
대시보드는 왜 필요한가요? 앱이 현장에서 감지한 결과와 GPS를 기록으로 보여주어 시연, 운영, 개선 근거를 제공합니다.
정책 JSON은 왜 쓰나요? 위험 클래스와 거리 기준을 코드에 흩뿌리지 않고 Android와 서버가 같은 기준을 쓰게 하기 위해서입니다.

17. 최종 체크리스트

아래 항목을 체크할 수 있으면 프로젝트 공부가 꽤 탄탄해진 상태입니다.

구조 이해

  • 프로젝트를 1분 안에 설명할 수 있다.
  • Android와 서버 역할을 분리해서 설명할 수 있다.
  • 카메라 프레임이 TTS 안내가 되는 흐름을 말할 수 있다.
  • 서버가 YOLO 추론 서버가 아니라는 점을 설명할 수 있다.

코드 이해

  • Detection.kt의 필드 의미를 안다.
  • TfliteYoloDetector.kt가 모델 로딩, 전처리, 추론, 후처리를 맡는다는 것을 안다.
  • MvpPipeline.kt가 위험도와 진동 패턴을 만든다는 것을 안다.
  • SentenceBuilder.kt가 TTS 문장을 만든다는 것을 안다.
  • src/api/routes.py의 주요 endpoint를 설명할 수 있다.

검증 이해

  • 문장 생성 테스트가 무엇을 확인하는지 안다.
  • API 테스트가 무엇을 확인하는지 안다.
  • Android 빌드 실패가 모델 문제가 아니라 SDK license 문제일 수 있음을 안다.
  • 성능 리포트의 FPS와 지연시간을 발표 근거로 사용할 수 있다.
마지막 목표: 코드를 다 외우는 것이 아니라, “사용자 경험 → Android 처리 → 모델 추론 → 후처리 → 서버 기록 → 검증” 순서로 질문이 들어와도 차분하게 따라가며 설명할 수 있는 상태입니다.
