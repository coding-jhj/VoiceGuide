VoiceGuide 프로젝트 구조 및 코드 이해서

이 문서는 “시각장애인용 지능형 웨어러블 가이드 서비스”를 강사님, 심사위원, 팀원이 모두 이해할 수 있게 Android 앱, YOLO 추론, 위험도 판단, 음성 안내, 서버, DB, 테스트를 하나의 흐름으로 설명합니다.

1. 프로젝트 한 줄 요약

VoiceGuide는 스마트폰 카메라로 주변 물체를 실시간 인식하고, 위험한 물체는 음성·진동으로 즉시 알려주며, 필요하면 서버에 탐지 결과와 GPS를 보내 대시보드에서 이동 기록과 위험 구간을 확인할 수 있게 하는 보행 보조 앱입니다.

사용자 관점

앱을 켜고 걸으면 주변 장애물, 차량, 사람, 생활 물체를 음성으로 안내받습니다. “이거 뭐야”, “의자 찾아줘” 같은 명령도 처리합니다.

기술 관점

Android에서 CameraX 프레임을 받아 TFLite YOLO 모델로 온디바이스 추론하고, 자체 파이프라인이 위험도·거리·진동 패턴을 계산합니다.

서버 관점

서버는 이미 탐지된 JSON을 받아 정규화, 추적, 저장, 대시보드 브로드캐스트를 담당합니다. 서버가 이미지 추론을 대신하지 않습니다.

공모전 관점

핵심 차별점은 “실시간성”, “경고 피로도 감소”, “물건 확인 기능”, “온디바이스 추론”, “설명 가능한 위험도 판단”입니다.

2. 전체 구조

프로젝트는 크게 Android 앱과 Python 서버로 나뉩니다. Android 앱은 실제 사용자 경험을 담당하고, Python 서버는 운영 기록, 대시보드, 정책 동기화, 검증용 API를 담당합니다.

1단계 CameraX가 카메라 프레임을 가져옵니다.
2단계 TfliteYoloDetector가 프레임을 YOLO 입력 크기에 맞춰 전처리하고 TFLite 추론을 수행합니다.
3단계 탐지 결과는 Detection 데이터 구조로 변환됩니다.
4단계 MvpPipeline이 IoU 추적, EMA smoothing, 거리 추정, 위험도, 진동 패턴을 계산합니다.
5단계 SentenceBuilder가 TTS로 읽을 한국어 문장을 만듭니다.
6단계 MainActivity가 화면, TTS, 진동, 서버 업로드, GPS를 제어합니다.
7단계 서버는 JSON을 받아 DB에 저장하고 대시보드에 SSE로 전달합니다.

4. 핵심 실행 흐름

일반 장애물 안내 흐름

  1. 사용자가 분석 시작 버튼을 누르거나 음성으로 시작합니다.
  2. MainActivity.startCamera()가 Preview, ImageCapture, ImageAnalysis를 바인딩합니다.
  3. analyzeStreamFrame()이 실시간 프레임을 받아 processOnDevice()로 넘깁니다.
  4. TfliteYoloDetector.detect()가 YOLO 추론을 수행합니다.
  5. 탐지 결과는 vote, duplicate removal, MVP pipeline을 거칩니다.
  6. 가장 중요한 객체만 문장화하고, TTS·진동으로 안내합니다.
  7. 필요한 프레임만 서버에 JSON으로 업로드합니다.

“이거 뭐야” 물건 확인 흐름

  1. STT 결과가 들고있는것 모드로 분류됩니다.
  2. 앱은 사진 저장 흐름 대신 다음 ImageAnalysis 스트림 프레임을 즉시 사용합니다.
  3. YOLO 결과 중 화면에서 가장 크게 잡힌 물체를 우선 선택합니다.
  4. SentenceBuilder.buildHeld()가 “손에 들고 있는 건 컵이에요” 같은 답변을 만듭니다.
  5. forceSpeak로 즉답 안내가 TTS busy 상태에 묻히지 않게 처리합니다.

찾기 모드 흐름

  1. 사용자가 “의자 찾아줘”처럼 말하면 extractFindTarget()가 찾을 대상을 뽑습니다.
  2. 탐지 목록에서 대상과 부분 일치하는 물체를 찾습니다.
  3. 찾으면 위치와 거리를 말하고, 못 찾으면 다른 방향을 보여달라고 안내합니다.
  4. 대상보다 더 가까운 위험물이 있으면 함께 경고합니다.
공모전 발표에서는 “YOLO를 돌린다”보다 “YOLO 결과를 사용자 행동으로 바꾸는 후처리 파이프라인이 있다”는 점을 강조해야 합니다. 탐지 모델 자체보다 제품 완성도를 보여주는 부분이기 때문입니다.

Android 앱에서 가장 큰 파일은 MainActivity.kt입니다. 이 파일은 단순 화면 코드가 아니라 카메라, STT, TTS, 진동, GPS, 서버 통신, 온디바이스 추론을 모두 연결하는 앱의 중앙 제어 장치입니다.

실제 코드 핵심 1: 프레임 분석 루프

앱은 매 프레임을 무조건 서버로 보내지 않습니다. 먼저 온디바이스에서 YOLO 추론을 수행하고, 앱이 필요한 판단을 한 뒤, 서버에는 정리된 JSON만 보냅니다. 이 구조 덕분에 네트워크가 불안정해도 기본 안내가 가능합니다.

실제 코드 핵심 2: 시작 음성 명령 레이스 방지

최근 수정된 중요한 부분입니다. 앱 시작 안내 중 사용자가 “이거 뭐야”라고 말하면, 카메라 바인딩이 끝나기 전에 명령이 처리되어 기본 장애물 안내처럼 보일 수 있었습니다. 그래서 시작 중 들어온 명령은 pendingStartupCommand에 보관하고, 분석 시작 후 다시 처리하게 했습니다. 

@Volatile private var pendingStartupCommand: String? = null

// 시작 확인 중 일반 명령이 들어오면 즉시 처리하지 않고 보관
pendingStartupCommand = text
requestPermissions()

// startAnalysis 이후 카메라가 준비된 다음 실제 명령 처리
val startupCommand = pendingStartupCommand
if (startupCommand != null) {
    pendingStartupCommand = null
    handler.postDelayed({ handleSttResult(startupCommand) }, 300L)
} else {
    scheduleAutoListen()
}

6. YOLO/TFLite 추론 구조

TfliteYoloDetector.kt는 모델 로딩, 프레임 전처리, TFLite 실행, 후처리를 담당합니다. 여기서 중요한 점은 “모델을 호출한다”가 아니라 “카메라 프레임 좌표와 YOLO 입력 좌표를 정확히 맞추고, 다시 화면 좌표로 되돌린다”입니다.

모델 선택

앱은 assets에 있는 모델 중 사용 가능한 모델을 선택합니다. 현재 구조는 yolo11n_320.tflite를 우선 사용하고, 필요 시 yolo26n_float32.tflite를 fallback으로 사용할 수 있게 되어 있습니다. 

modelName = listOf("yolo11n_320.tflite", "yolo26n_float32.tflite").firstOrNull { name ->
    try { context.assets.open(name).close(); true }
    catch (_: Exception) { false }
} ?: throw IllegalStateException("TFLite model file is missing")

전처리 개념: Letterbox

카메라 화면은 640x480, 1280x720처럼 가로세로 비율이 다양하지만 YOLO 모델은 정사각형 입력을 기대합니다. 그래서 이미지를 찌그러뜨리지 않고 비율을 유지한 채 축소하고, 남는 공간은 padding으로 채웁니다. 이것을 letterbox라고 부릅니다. 

val scale = minOf(inputSize.toFloat() / origW, inputSize.toFloat() / origH)
val scaledW = (origW * scale + 0.5f).toInt()
val scaledH = (origH * scale + 0.5f).toInt()
val padX = (inputSize - scaledW) / 2
val padY = (inputSize - scaledH) / 2

왜 바운딩 박스가 틀어질 수 있는가

바운딩 박스 정확도는 모델 성능만의 문제가 아닙니다. 다음 중 하나라도 어긋나면 박스가 이상하게 보입니다.

  • 카메라 회전값을 반영하지 않음
  • letterbox padding을 빼지 않고 좌표를 복원함
  • PreviewView가 화면을 crop하는 방식과 overlay가 그리는 방식이 다름
  • 모델 출력 형식이 raw YOLO인지 end-to-end NMS인지 구분하지 않음
  • NMS IoU threshold가 너무 낮거나 높음

현재 코드는 회전, padding, raw output, end-to-end output, class-aware NMS를 고려합니다. 다만 실기기에서는 PreviewView의 실제 crop과 overlay 좌표가 맞는지 계속 확인해야 합니다.

후처리: raw output과 end-to-end output

출력 방식 코드 설명
Raw YOLO postProcessRaw 출력 shape이 [1, 84, N]인 경우입니다. 클래스 점수 중 가장 높은 것을 고르고 NMS를 직접 수행합니다.
End-to-end NMS postProcessEndToEnd 출력 row가 [x1, y1, x2, y2, score, classId] 형태인 경우입니다.

성능 포인트

  • ImageAnalysis.STRATEGY_KEEP_ONLY_LATEST로 밀린 프레임을 쌓지 않습니다.
  • RGBA 입력이면 YUV 변환보다 빠르게 처리할 수 있습니다.
  • GPU delegate가 가능하면 GPU를 쓰고, 실패하면 XNNPACK CPU로 fallback합니다.
  • Sampling plan을 캐싱해서 매 프레임 좌표 계산 비용을 줄입니다.
  • 탐지 결과는 최대 8개만 유지해서 TTS와 서버 업로드가 무거워지지 않게 합니다.

7. 위험도·추적·진동 파이프라인

MvpPipeline.kt는 공모전에서 꼭 설명해야 하는 핵심입니다. YOLO는 “무엇이 어디에 있다”만 알려줍니다. 하지만 시각장애인 보행 보조 서비스는 “얼마나 위험한가”, “계속 같은 물체인가”, “음성으로 말해야 하는가, 진동만 줘야 하는가”를 판단해야 합니다.

IoU 추적

같은 클래스의 박스가 이전 프레임의 박스와 충분히 겹치면 같은 물체로 봅니다. 이때 사용하는 지표가 IoU입니다. IoU는 두 박스가 겹친 면적을 두 박스의 합집합 면적으로 나눈 값입니다. 

private const val IOU_MATCH_THRESHOLD = 0.25f

if (tr.cls != detections[di].classKo) continue
val score = iou(detections[di], tr)
if (score >= IOU_MATCH_THRESHOLD) {
    // 같은 물체 track으로 연결
}

EMA smoothing

YOLO 박스는 실제로 가만히 있어도 프레임마다 조금씩 흔들립니다. 이 흔들림이 그대로 TTS에 반영되면 사용자는 계속 다른 안내를 듣게 됩니다. EMA는 현재 값과 이전 값을 섞어서 부드럽게 만드는 방식입니다. 

track.cx = EMA_ALPHA * det.cx + (1f - EMA_ALPHA) * track.cx
track.cy = EMA_ALPHA * det.cy + (1f - EMA_ALPHA) * track.cy
track.w = EMA_ALPHA * det.w + (1f - EMA_ALPHA) * track.w
track.h = EMA_ALPHA * det.h + (1f - EMA_ALPHA) * track.h

위험도 계산

위험도는 단순 confidence가 아닙니다. confidence는 “모델이 이 물체를 얼마나 확신하는가”이고, risk score는 “사용자에게 얼마나 위험한가”입니다.

요소 의미 예시
거리 가까울수록 위험 0.8m 이내는 강한 위험
중앙성 화면 중앙에 가까울수록 진행 방향 위험 정면 의자, 정면 차량
클래스 가중치 차량·동물·계단 등은 더 위험 버스, 자동차, 계단
박스 크기 화면에서 크게 보이면 가까울 가능성이 큼 큰 의자 박스, 가까운 사람

진동 패턴

패턴 상황 의도
NONE 생활 물체 또는 낮은 위험 불필요한 경고 피로도 감소
SHORT 주의 필요 가벼운 비음성 알림
DOUBLE 위험도 중간 이상 사용자가 즉시 주의하도록 함

TTS 경고 피로도 감소

경고 피로도는 이 프로젝트에서 매우 중요한 문제입니다. 계속 “의자가 있어요, 의자가 있어요”라고 말하면 사용자가 앱을 신뢰하지 않게 됩니다. 그래서 프로젝트는 다음 방법으로 피로도를 줄입니다.

  • 같은 클래스는 일정 시간 안에 반복 발화하지 않음
  • 생활 물체는 위험도가 낮으면 진동을 주지 않음
  • 위험하지 않은 먼 물체는 beep 또는 silent 처리
  • 질문/물건 확인처럼 사용자가 명시적으로 물어본 경우만 즉답
  • TTS busy 상태에서 일반 안내는 drop하고, 물건 확인 답변은 force speak로 우선 처리

11. 정책 파일과 SSOT

src/config/policy.json과 Android의 policy_default.json은 프로젝트의 판단 기준을 담고 있습니다. 여기서 SSOT는 Single Source of Truth, 즉 “판단 기준을 한 곳에서 관리한다”는 뜻입니다.

정책에 들어 있는 내용

항목 설명
classes.vehicle_ko 차량으로 취급할 클래스 목록입니다. 자동차, 버스, 트럭, 오토바이 등이 여기에 들어갑니다.
classes.critical_ko 거리와 무관하게 위험하게 볼 수 있는 클래스 목록입니다.
classes.everyday_ko 컵, 의자, 책 등 생활 물체입니다. 물건 확인에는 중요하지만 불필요한 긴급 경고는 줄여야 합니다.
alert_mode 차량, 동물, 일반 물체가 어느 거리 이내일 때 critical/beep가 되는지 정합니다.
distance_format 거리 표현을 “코앞”, “약 1.5미터”처럼 바꾸는 기준입니다.
on_device Android 온디바이스 판단에 필요한 bbox 기반 거리 보정, 찾기/물건 확인 임계값이 들어 있습니다.

왜 정책 분리가 중요한가

  • 위험 기준을 코드 수정 없이 조정할 수 있습니다.
  • Android와 서버가 같은 판단 기준을 공유할 수 있습니다.
  • 공모전 피드백을 받았을 때 “어디를 조정해야 하는지” 설명하기 쉽습니다.
  • 경고 피로도와 민감도를 실험하면서 개선할 수 있습니다.

13. 공모전 설명 전략

공모전에서는 기능을 많이 나열하는 것보다, 문제 정의와 해결 방식이 명확해야 합니다. 이 프로젝트는 다음 네 가지 축으로 설명하는 것이 가장 좋습니다.

1. 시각장애인 보행 보조의 실제 문제

  • 카메라가 물체를 인식해도 너무 자주 말하면 오히려 방해가 됩니다.
  • 네트워크가 불안정하면 서버 추론 방식은 즉시성이 떨어집니다.
  • 사용자는 “주변 전체 설명”뿐 아니라 “내가 손에 든 물건 확인”도 필요합니다.
  • 위험한 물체와 단순 생활 물체를 구분해야 합니다.

2. VoiceGuide의 해결 방식

  • 온디바이스 YOLO/TFLite로 기본 안내를 기기 안에서 처리합니다.
  • IoU tracking과 EMA smoothing으로 흔들림을 줄입니다.
  • risk score와 vibration pattern으로 경고를 단계화합니다.
  • STT 명령으로 일반 안내, 찾기, 질문, 물건 확인을 전환합니다.
  • 서버와 대시보드로 운영 로그와 위치 기반 분석을 제공합니다.

3. 심사위원에게 보여줄 데모 순서

  1. 앱 실행 후 일반 안내 시작
  2. 의자나 사람을 카메라에 비추고 방향·거리 안내 확인
  3. “이거 뭐야” 발화 후 물건 확인 답변 확인
  4. “의자 찾아줘” 발화 후 찾기 모드 확인
  5. 대시보드에서 실시간 세션, GPS, 탐지 히스토리 확인
  6. 성능 리포트에서 FPS와 추론 시간 설명

4. 약점도 솔직하게 말하되 개선 방향을 제시

약점 현재 대응 추가 개선 방향
거리 추정은 단안 카메라 bbox 기반이라 완전 정확하지 않음 bbox 면적, 클래스별 보정값, clamp로 안정화 Depth API 또는 LiDAR/스테레오 센서 연계
YOLO 모델이 모든 물체를 완벽히 잡지는 못함 confidence, NMS, vote, tracking으로 안정화 공모전 시나리오 중심 데이터 fine-tuning
음성 안내가 많으면 피로해짐 cooldown, silent/beep/critical 단계화 사용자별 민감도 설정 추가
실기기마다 FPS 편차가 있음 stream frame 즉시 처리, keep latest, TFLite delegate 사용 기기별 프로파일링 및 입력 해상도 자동 조절

15. 핵심 코드 빠른 색인

파일 꼭 봐야 할 코드 한 줄 설명
MainActivity.kt handleSttResult 음성 명령을 앱 모드로 바꾸는 중심 함수입니다.
MainActivity.kt processOnDeviceInternal YOLO 결과를 화면, TTS, 진동, 서버 업로드로 연결합니다.
MainActivity.kt requestImmediateStreamFrame 물건 확인처럼 즉답이 필요한 모드에서 다음 스트림 프레임을 사용합니다.
TfliteYoloDetector.kt detect, runModel, postProcessRaw, nms TFLite YOLO 추론의 전처리, 실행, 후처리입니다.
MvpPipeline.kt update, computeRisk, patternFor 추적, 위험도, 진동 패턴을 계산합니다.
SentenceBuilder.kt build, buildFind, buildHeld 온디바이스 한국어 안내 문장을 만듭니다.
VoicePolicy.kt applyFromServerJson, calcDistBboxM 서버 정책을 Android에 반영하고 bbox 기반 거리를 계산합니다.
routes.py detect, detect_from_json, answer_question Android가 보내는 탐지 JSON을 처리합니다.
tracker.py SessionTracker.update 서버 쪽 세션별 객체 상태를 안정화합니다.
db.py init_db, enqueue_detection_event, save_performance_metric 탐지 이벤트, 성능, GPS, 경고 판단을 저장합니다.

팀원이 반드시 설명할 수 있어야 하는 질문

  1. 왜 서버 추론이 아니라 온디바이스 추론인가?
  2. YOLO confidence와 서비스 risk score는 어떻게 다른가?
  3. 바운딩 박스가 틀어지는 원인은 무엇이고, 이 프로젝트는 어떻게 보정하는가?
  4. “이거 뭐야”는 일반 장애물 안내와 무엇이 다른가?
  5. 경고 피로도를 줄이기 위해 어떤 장치를 넣었는가?
  6. 서버와 대시보드는 사용자 앱의 필수 기능인가, 운영/검증 기능인가?
  7. 실기기에서 FPS가 떨어질 때 어디부터 확인해야 하는가?

실기기 FPS 문제 체크 순서

  1. 로그에서 preprocess_ms, infer_ms, postprocess_ms를 분리해서 봅니다.
  2. infer_ms가 크면 모델/delegate/입력 크기 문제입니다.
  3. preprocess_ms가 크면 YUV/RGBA 변환, 회전, resize 비용을 봅니다.
  4. 전체 FPS만 낮고 추론 시간은 괜찮으면 TTS, 서버 업로드, UI update, in-flight 누적을 봅니다.
  5. 물건 확인 모드만 느리면 사진 저장 흐름을 타는지, 스트림 프레임 즉시 처리 흐름을 타는지 확인합니다.
이 문서는 코드 설명용입니다. 발표 자료로 바꿀 때는 여기서 “문제 정의 → 해결 구조 → 데모 → 성능 → 한계와 개선”만 뽑아 슬라이드로 만들면 됩니다.
