VoiceGuide 데이터 비교 계획

두 ZIP과 현재 전처리 결과를 비교해 좋은 점만 합치는 계획

목표는 데이터를 더 많이 모으는 것이 아니라, 발표 시나리오에서 바로 설명 가능한 최종 데이터셋을 만드는 것이다. 따라서 채택 기준은 “시나리오에 바로 쓰이는가”, “근거가 남는가”, “지도와 대시보드에 연결하기 쉬운가”로 둔다.

결론

현재 우리가 만든 전처리 결과를 기준본으로 두고, voiceguide_scenario.zip의 GeoJSON, 추천 등급, 근거 문구 구조를 흡수한다. voiceguide전처리.zip에서는 데모 HTML 구성과 단순한 컬럼명 방식을 참고한다.

단, 외부 ZIP의 90m A/B 예시는 그대로 쓰지 않는 것이 좋다. 해당 예시는 사당동 횡단보도 쌍 기준이고, 현재 우리가 고정한 “보라매역 → 서울시남부장애인종합복지관” 시나리오와 직접 연결되지 않는다.

자료별 좋은 점

현재 우리 결과

기준본으로 사용

원본 역할별 폴더가 분명하고, 동작구 복지관과 횡단보도 점수표, 실제 시나리오 A/B 비교 파일, 지도 마커, TTS 문장까지 연결되어 있다.

voiceguide_scenario.zip

지도와 발표 설명에 강함

동작구 횡단보도 1,025건을 GeoJSON으로 제공하고, support_evidence, route_recommendation_tier처럼 발표에서 바로 읽기 좋은 컬럼이 있다.

voiceguide전처리.zip

화면 예시와 단순 컬럼에 강함

demo_A_step_flow.html, demo_B_dashboard.html, demo_C_app_simulator.html가 있어 발표 화면 구성을 참고하기 좋다.

최종 통합 산출물 설계

최종 폴더는 data/processed/voiceguide_final처럼 새로 만들고, 기존 산출물은 건드리지 않는 방식이 좋다. 그래야 원본 전처리와 통합본을 비교하기 쉽다.

파일 용도 가져올 장점
final_route_comparison.csv 발표 핵심 A/B 경로 비교표 우리 A/B 구조 + scenario ZIP의 근거 문구 방식
final_crosswalk_accessibility.csv 동작구 횡단보도 전체 점수표 우리 매칭 결과 + traffic safety 상세 컬럼 + 추천 등급
final_crosswalk_accessibility.geojson 지도 표시용 횡단보도 포인트 scenario ZIP의 GeoJSON 구조
final_scenario_dataset.json 앱/대시보드가 한 번에 읽는 대표 JSON scenario ZIP의 JSON 패키징 방식
final_tts_guidance.csv 사용자에게 말할 문장 우리 TTS 문장 + 지원시설 근거 문구
final_data_usage.html 교수님/팀원에게 보여줄 데이터 사용 설명 scenario ZIP의 설명 HTML + 우리 실제 파일 경로

작업 순서

1단계

컬럼 표준 정하기

횡단보도는 crosswalk_id, district, address, latitude, longitude, has_pedestrian_light, has_audio_signal, has_push_button, accessibility_score, support_evidence로 맞춘다.

우선순위 높음

2단계

점수 체계 합치기

현재 점수는 유지하되, scenario ZIP의 has_traffic_safety_detail을 추가한다. 최종 점수는 보행등, 음향신호기, 보행자작동신호기, 고원식, 교통안전시설 상세를 반영한다.

우선순위 높음

3단계

GeoJSON 만들기

동작구 횡단보도 전체와 A/B 대표 횡단보도를 지도에 바로 올릴 수 있게 GeoJSON으로 만든다.

우선순위 중간

4단계

대표 JSON 패키지 만들기

목적지 후보, 추천 횡단보도 후보, A/B 비교, TTS 문장, 이동지원센터 fallback을 final_scenario_dataset.json 하나에 묶는다.

우선순위 높음

5단계

발표용 HTML 정리

voiceguide전처리.zip의 데모 화면 구조를 참고해서, 최종 데이터가 어떤 근거로 경로 B를 선택하는지 보여주는 HTML을 만든다.

우선순위 중간

채택하지 않을 것

90m 문구를 그대로 쓰지 않는다. 외부 ZIP의 90m 예시는 “횡단보도 점 사이의 직선거리”에 가깝고, 우리가 잡은 보라매역-남부장애인종합복지관 시나리오의 실제 보행 우회거리로 검증된 값이 아니다.
  • API로 실제 보행거리를 계산하기 전까지는 “정확한 최단 경로”라고 말하지 않는다.
  • 서울 이동지원센터를 1개만 남기지 않는다. 우리 데이터처럼 후보를 넓게 유지한다.
  • 좌표 변환 근거가 불명확한 파일은 최종 기준본으로 쓰지 않고 참고 자료로만 둔다.

발표에서 말할 수 있는 문장

“공공데이터를 목적지, 횡단보도, 보행지원시설, 이동지원센터로 나눈 뒤, 동작구 시나리오에 맞춰 횡단보도별 보행지원 점수를 계산했습니다. 최종 데이터셋은 최단 후보 경로와 보행지원시설이 있는 안전 후보 경로를 비교할 수 있도록 CSV, GeoJSON, JSON, 안내문 형태로 구성할 계획입니다.”
